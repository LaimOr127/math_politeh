# Правила работы с проектом

## Цель

Проект объясняет Python детям 10-12 лет через связанные пособие, уроки и игровой сайт. Любое изменение должно сохранять совпадение формулировок, кода и ожидаемых результатов во всех трёх форматах.

## Перед изменением

1. Прочитайте `docs/ARCHITECTURE.md`, `docs/CONTENT_MODEL.md` и соответствующую ADR.
2. Найдите все упоминания изменяемой миссии, команды Python или контракта через `rg`.
3. Для нового поведения сначала добавьте или обновите тест.

## Код сайта

- Не читайте и не записывайте `localStorage` вне `site/src/storage/ProgressStore.js`; интерфейс может только передать браузерный адаптер в конструктор `ProgressStore`.
- Не копируйте обработчики и разметку между миссиями: данные миссии живут в `site/src/data/missions.js`.
- Добавляйте класс только для устойчивой предметной сущности. Не создавайте абстракции «на будущее».
- У публичных функций и классов обязателен JSDoc с параметрами, результатом и побочным эффектом.
- Не добавляйте зависимости без явной необходимости и записи в ADR.
- Поддерживайте клавиатурную навигацию, видимый фокус и `prefers-reduced-motion`.

## Документация

При изменении модуля обновите `docs/API.md`. При смене слоёв, формата данных или важного решения обновите `docs/ARCHITECTURE.md` или добавьте ADR. Изменение учебной миссии требует обновить `docs/CONTENT_MODEL.md` и связанные материалы урока.

## Проверка

Запустите `npm run check`. Затем вручную пройдите изменённую миссию в браузере, включая неправильный ответ, повторное нажатие «Проверить», сброс и навигацию только с клавиатуры.

## Навыки и инструменты разработки

- Автоматически применять релевантные навыки ponytail, ponytail-review, security-best-practices, frontend-design и web-design-guidelines. Сохранять требования этого проекта к JSDoc, структуре, учебному содержанию и проверкам.
- Вопросы по API библиотек проверять через Context7, если он подключён; иначе использовать официальную документацию. Не добавлять библиотеку только ради применения навыка.
- Для сложных связей модулей использовать локальный Graphify в режиме --code-only; подтверждать связи исходниками и учитывать дату построения графа. Для точечного поиска использовать rg.
- Визуальное направление проекта: космический стиль, аудитория 10–12 лет, переключение светлой и тёмной тем, адаптивность и доступность.
- Состав, версии, ограничения и команды инструментов описаны в docs/DEVELOPMENT_TOOLS.md.

## Сохранение изменений и GitHub

- Пользователь просит хранить изменения локально и отправлять их в Git-репозиторий проекта. После завершённой и проверенной задачи сохранять относящиеся к ней файлы, создавать осмысленный коммит и выполнять обычный push в соответствующую ветку без повторного запроса разрешения.
- Перед коммитом проверять состав изменений, актуальность удалённой ветки и необходимые проверки проекта. Посторонние пользовательские изменения не включать. Секреты, .env, кэши, зависимости и временные результаты не публиковать; шаблоны настроек без секретов допустимы.
- Не использовать force push и не переписывать чужую историю. Если push не удался, сохранить локальный коммит, точно сообщить о причине и о том, что удалённый репозиторий ещё не обновлён. Не заявлять об отправке без успешного результата и проверки удалённого commit.
- Учётные данные при необходимости запрашивать защищённым инструментом; не просить пароли или токены в обычном сообщении.
